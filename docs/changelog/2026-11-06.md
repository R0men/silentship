# 2026-11-06

### [Bug Fix] A rollout completes only after enough different edges saw it

- **Files:** `backend/src/pipeline/rollouts.js`, `backend/src/pipeline/run.js`, `backend/test/rollouts.test.js`, `docs/architecture/rollouts.md`, `docs/architecture/data.md`, `README.md`
- **Why:** all samples of a run can land on one edge, so three runs at 100% proved little: `office.js` of 16.0.20626 went complete at 63% on a single edge, and 218 of 228 past completions had seen fewer than 8 edges.
- **What:** complete now takes 6 runs at 100% on at least 12 different edges, or 36 runs at 100% whatever the edge count, so a small edge pool cannot block it forever. Without any edge ids in the responses the runs alone decide. Rollouts store `fullEdges`.

### [Bug Fix] OneCDN builds get complete API diffs

- **Files:** `backend/src/analysis/surface-worker.js`, `backend/src/analysis/surface-runner.js`, `backend/src/pipeline/run.js`, `backend/test/surface-runner.test.js`
- **Why:** an unhandled rejection from OneCDN's loader ended the worker while a large result was still going out on the pipe, so most OneCDN files failed. The error kept the first bytes of stderr, which were Microsoft's minified code rather than the reason, and a failed diff read as "this build changes nothing".
- **What:** the worker ignores such rejections, since the surface is already built by then. `workerReason` keeps only short stderr lines. A failed diff sets the note "API diff failed; changes in this file are unknown". Releases already stored stay incomplete (known issues).

### [Feature] Release and API type pages explain a lowered severity

### [Infra] Fewer database reads and writes, to stay within the free tier

- **Files:** `backend/src/web/run-cache.js`, `backend/src/web/server.js`, `backend/src/web/live.js`, `backend/src/db.js`, `backend/src/pipeline/rollouts.js`, `backend/src/pipeline/run.js`, `backend/test/free-tier.test.js`, `docs/architecture/web.md`, `docs/architecture/data.md`, `docs/architecture/alerts.md`, `docs/tasks/PLAN.md`
- **Why:** one page cost dozens of database round trips, each run loaded full rollout histories, and `snapshots` grew by a row per file per run on a database limited to 512 MB.
- **What:** read routes are reused until the live feed's version changes (`createRunCache`), and `/api/home` and `/api/overview` come from the live snapshot, rebuilt at least every 5 minutes. Runs load only the history the smoothed share needs. `snapshots` keep only informative runs (`keepSnapshot`), and their TTL is 30 days instead of 90 (`ensureTtlIndex` changes an existing index in place).

### [Infra] Snapshots outlive the TTL: daily files, read together with MongoDB

- **Files:** `deploy/backup.sh`, `backend/src/archive/snapshot-history.js`, `backend/src/cli.js`, `backend/src/config.js`, `backend/package.json`, `backend/test/snapshot-history.test.js`, `README.md`, `docs/SETUP.md`, `docs/architecture/data.md`, `docs/tasks/PLAN.md`
- **Why:** with a 30-day TTL and rotating dumps, per-run samples had no long-term copy, and planned work on CDN incidents needs them. Nobody should have to track when a row expires.
- **What:** the nightly backup exports each finished day to `snapshots/<date>.jsonl.gz`, never rotated; any day inside the TTL without a file is exported, so the first run and a missed night catch up. `readSnapshots` joins MongoDB and those files, counting a row in both once; by hand, `npm run snapshots -w backend`.

### [Infra] A failed nightly backup pings the healthcheck

- **Files:** `deploy/backup.sh`, `docs/SETUP.md`
- **Why:** a failure was visible only in the service log, which nobody reads every night.
- **What:** with `HEALTHCHECK_URL`, any failed run pings `<url>/fail`, including one that stops at `mongodump`. The next crawl's ping marks the check up again, so it arrives as one notification. A run that never starts sends nothing.

- **Files:** `frontend/app/reference/page.js`, `frontend/components/HubFilter.js`, `frontend/app/globals.css`, `backend/src/analysis/apps.js`, `backend/src/web/queries.js`, `docs/architecture/frontend.md`, `docs/architecture/web.md`
- **Why:** the hub listed every changed type of every application together; a developer of a Word or PowerPoint add-in had to scan Excel changes to find theirs.
- **What:** a second filter row: All apps, Excel, Word, PowerPoint, Outlook, OneNote, Visio, Common API (only those with changes), combined with "Documented only". Build headers, "Older builds" and the A–Z index follow the chosen application, with counts and severity per application. "1 type" instead of "1 types"; an A–Z group with only undocumented types no longer leaves an empty heading under "Documented only".

### [Feature] Alerts for chosen applications

- **Files:** `backend/src/analysis/apps.js`, `backend/src/notify/settings.js`, `backend/src/notify/alerts.js`, `backend/src/notify/email-templates.js`, `backend/src/web/server.js`, `frontend/components/Settings.js`, `frontend/app/globals.css`, `backend/test/delivery.test.js`, `TECH.md`, `docs/architecture/alerts.md`, `docs/architecture/web.md`, `docs/architecture/README.md`
- **Why:** a subscriber who builds for one application got every alert about the others; the watchlist needs exact API paths, which most people will not write.
- **What:** "Applications" checkboxes on `/settings` (several at once; all ticked = no filter, stored as `[]`). Like the watchlist, and together with it, only API changes in the chosen applications count, the severity is theirs, and a build with none is not emailed; rollbacks follow the same rule, loader-flags-changed still goes to everyone. The email heading says "API changes in Excel and Word". Slack is unchanged.

### [Feature] Sign-in to alert settings by email code; the browser remembers the subscriber

- **Files:** `backend/src/web/server.js`, `backend/src/notify/email-templates.js`, `backend/src/notify/alerts.js`, `backend/src/cli.js`, `frontend/components/SignIn.js`, `frontend/components/Settings.js`, `frontend/components/Subscribe.js`, `frontend/lib/account.js`, `frontend/app/layout.js`, `frontend/app/settings/page.js`, `frontend/app/privacy/page.js`, `frontend/app/globals.css`, `backend/test/delivery.test.js`, `TECH.md`, `docs/architecture/alerts.md`, `docs/architecture/web.md`, `docs/architecture/frontend.md`
- **Why:** the settings were reachable only from the link in an email, so most subscribers would never learn they exist.
- **What:** confirming a subscription opens `/settings` with "You're subscribed" instead of the home page. "Alerts" in the nav and "Manage your alerts" under the subscribe form open `/settings`; without a remembered token it asks for the email: a subscribed address gets a 6-digit code and a "Manage alerts" button (`POST /api/signin`, `/api/signin/verify`; code hashed, 15 minutes, 5 guesses, used once; the subscribe form's email limits), any other address gets the confirmation email; the reply is the same either way. The token is kept in localStorage and removed from the address bar; "Forget this browser" clears it, and a token the API refuses is forgotten. A remembered subscriber sees their address instead of the subscribe form. `/privacy` mentions the local storage; `mail-preview` includes the sign-in email.

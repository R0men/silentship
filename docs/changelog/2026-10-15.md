### [Infra] Repository, CI and automatic deploys

- **Files:** `.github/workflows/ci.yml`, `.github/dependabot.yml`, `deploy/deploy.sh`, `deploy/silentship.service`, `.gitignore`, `.gitattributes`, `docs/SETUP.md`
- **Why:** the code only existed on a laptop and reached the server by hand; the server's copy was not a git checkout.
- **What:**
  - GitHub repository `R0men/silentship`, `main` = production; made public with MIT license, `SECURITY.md`, `CONTRIBUTING.md`.
  - CI on every push and PR: `npm ci` → `npm test` → `npm run build`; on `main` a `deploy` job (environment `production`, pinned host key).
  - The GitHub Actions key is limited on the server to a forced command, `deploy/deploy.sh`; the script deploys only commits on `origin/main`, runs `npm ci` only when the lockfile changed, waits for a running crawl before restarting (so the archive is never left with an `index.lock`) and checks that the API and the site respond.
  - A narrow sudoers rule lets the service user run only `systemctl restart silentship`.

### [Bug Fix] Rollout alerts need confirmation and API changes; rollbacks always alert

- **Files:** `backend/src/notify/alerts.js`, `backend/src/notify/email-templates.js`, `backend/src/cli.js`, `backend/test/pipeline.test.js`, `docs/architecture/alerts.md`, `docs/architecture/data.md`, `docs/tasks/PLAN.md`, `TECH.md`, `frontend/app/layout.js`, `frontend/app/opengraph-image.js`
- **Why:**
  - Every rollout emailed every subscriber without a watchlist, even with zero API changes (prod 16.0.20606: 26 files, 0 changes — it went out before anyone had confirmed, so nobody got it).
  - At 16:16 UTC five of eight edges returned 404 for `onenote-winrt-16.00.js` in one run and served it in every run after. That short CDN incident became a High "files removed" rollout alert to the one confirmed subscriber — wrong as a rollout alert, though the incident itself is real.
  - A build Microsoft pulls back never alerted at all: abandoned rollouts were skipped.
  - The site promised detection "within minutes"; alerts take ~30–40 minutes.
- **What:**
  - A group alerts as a rollout only after a version was seen in `CONFIRM_RUNS` (2) runs or completed (`groupConfirmed`); without a watchlist, email also requires API changes or High severity (`emailWorthy`). Slack keeps getting every confirmed group.
  - Rollbacks: a confirmed group whose files all went unserved for 24 h gets a "pulled back" email (`rollbackEmail`) to every channel subscriber — even with no API changes and regardless of `minSeverity` — plus Slack; `rollbackNotifiedAt` makes it alert once. `mail-preview` now sends a rollback sample too.
  - Single-run incidents stay in the data (not deleted) and are planned as their own site events (PLAN #10).
  - Wording: "checked every 10 minutes" on the site and the OG image; `TECH.md` states the real alert latency.
  - Dry run on production data: prod 20606 → no email, beta 20606 (44 changes, High) → email, the 404 incident → no email.

### [Bug Fix] The site shows only confirmed rollouts

  - The channel card names a group by its build, or "Files removed" / "Unversioned change", never by its key.
  - The 30-day stats count distinct builds, not groups; the second figure counts builds or other changes with High severity.
  - The first read-model test on an in-memory MongoDB.

### [Bug Fix] Email links no longer change a subscription on GET

- **Files:** `backend/src/web/server.js`, `backend/src/web/action-page.js`, `backend/test/delivery.test.js`, `docs/architecture/alerts.md`, `docs/architecture/web.md`, `docs/VERIFY.md`
- **Why:** corporate mail gateways (Defender Safe Links, Mimecast) open every link in an email to scan it. `GET /confirm` and `GET /unsubscribe` changed state, so a scanner could confirm an address someone else typed in, or unsubscribe a reader.
- **What:** a GET shows a page with a "Confirm" / "Unsubscribe" button; only its POST changes state (303 to `/?notice=…`). RFC 8058 one-click `POST /unsubscribe` still gets a plain 200.

### [Bug Fix] Alerts are queued and retried; one alert per build, then updates

- **Files:** `backend/src/notify/alerts.js`, `backend/src/notify/email-templates.js`, `backend/src/db.js`, `backend/test/delivery.test.js`, `docs/architecture/alerts.md`, `docs/architecture/data.md`
- **Why:**
  - A Brevo or Slack failure was logged and the rollout marked notified anyway: the alert was lost for good.
  - A build reaches files over hours (prod 16.0.20606: 14 files, then 26); every later batch went out as another alert with the same subject.
- **What:**
  - New collection `deliveries` (outbox, TTL 90 days): alerts are rendered per recipient and queued; `flushDeliveries` sends them after every crawl and retries failures on later crawls up to `MAX_ATTEMPTS` (24); emails to someone who unsubscribed meanwhile are dropped.
  - Later batches of an alerted build send only API changes not sent before, with "— update, N new API change(s)" in the subject; without new changes nothing is sent. The same for Slack.

### [Bug Fix] Subscribing an address that is already subscribed

- **Files:** `backend/src/web/server.js`, `backend/src/notify/email-templates.js`, `frontend/components/Subscribe.js`, `backend/test/delivery.test.js`, `docs/architecture/alerts.md`, `docs/architecture/data.md`
- **Why:** for a confirmed address the form said "we sent a confirmation link" but nothing was sent, and a newly ticked beta box was silently ignored.
- **What:** a confirmed address gets "You're already subscribed" (with an unsubscribe link); a newly requested channel waits in `pendingChannels` until the confirm button. The answer to the form is still the same for every address, so it reveals nobody; the form now says "we sent you an email".
